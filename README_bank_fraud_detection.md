# Bank Fraud Detection Pipeline — Snowflake

A hands-on Snowflake data engineering project demonstrating staged CSV ingestion, raw/staging/core/analytics layers, streams and tasks for incremental processing, dynamic tables for declarative analytics, and views for fraud monitoring.

> **Scope:** This is an educational demo using synthetic transactions and rule-based classifications. It is not a production fraud decisioning system. The `IS_FRAUD` field represents a supplied demo label; the risk score is synthetic and is not produced by a trained model.

## Architecture

```text
CSV file
  │
  ▼
Internal stage + CSV file format
  │ COPY INTO
  ▼
RAW.TRANSACTIONS_RAW
  │
  ├── STAGING.V_TRANSACTIONS_STANDARDIZED
  │
  └── Stream → Scheduled task → CORE.TRANSACTIONS
                                  │
                                  ├── Dynamic table: daily summary
                                  ├── Dynamic table: fraud risk by country
                                  ├── View: high-risk transactions
                                  └── View: dashboard KPIs
```

## Snowflake objects

| Object | Purpose |
|---|---|
| `FRAUD_WH` | Small auto-resuming compute warehouse |
| `FRAUD_DEMO.RAW` | Raw landing table, CSV format, internal stage, stream |
| `FRAUD_DEMO.STAGING` | Standardization and basic validation view |
| `FRAUD_DEMO.CORE` | Incrementally populated transaction table and task |
| `FRAUD_DEMO.ANALYTICS` | Dynamic tables and reporting views |

## Prerequisites

- A Snowflake account.
- A role with privileges to create a warehouse and database, plus schemas, stages, file formats, tables, streams, tasks, views, and dynamic tables.
- Use a least-privilege role in a shared or production account. The script's `USE ROLE ACCOUNTADMIN` is for a disposable personal demo only; remove it if your role is already configured.

## Quick start

1. Open a Snowflake SQL worksheet.
2. Open `bank_fraud_detection_pipeline.sql`.
3. Run sections **00–03** to create the environment, landing objects, and seed data.
4. Run section **04** to build the core table, stream, and task. Inspect the task definition before resuming it.
5. Run sections **05–06** to create dynamic tables and reporting views.
6. Run section **07** to verify row counts and analytics.
7. Run section **08** to export `FRAUD_DEMO.CORE.TRANSACTIONS` as a CSV file to the internal stage.
8. Run section **09** to inspect task and dynamic-table refresh history.

The script uses `CREATE OR REPLACE` for repeatable object definitions, but **re-running the entire script is not fully idempotent**: it can recreate objects and reseed rows. On a rerun, duplicate transaction IDs can occur because Snowflake standard-table primary/unique constraints are generally informational rather than enforced. Use a fresh database or remove/reseed the sample data deliberately.

## Loading a CSV

The SQL script creates an internal named stage and a CSV file format. Prepare a CSV with the 16 transaction fields in the same order as the raw table's explicit `COPY INTO` column list; do not include `INGESTED_AT`, which is generated by Snowflake.

From SnowSQL or Snowflake CLI, upload a local file:

```sql
PUT file://<absolute-path>/transactions.csv
  @FRAUD_DEMO.RAW.TRANSACTIONS_STAGE
  AUTO_COMPRESS=TRUE;
```

Then execute this in a worksheet:

```sql
COPY INTO FRAUD_DEMO.RAW.TRANSACTIONS_RAW
  (TRANSACTION_ID, TRANSACTION_TS, CUSTOMER_ID, ACCOUNT_ID, AMOUNT,
   CURRENCY, TRANSACTION_TYPE, MERCHANT_NAME, MERCHANT_CATEGORY, CITY,
   COUNTRY, DEVICE_ID, IP_ADDRESS, IS_FRAUD, RISK_SCORE, TRANSACTION_STATUS)
FROM @FRAUD_DEMO.RAW.TRANSACTIONS_STAGE
FILE_FORMAT = (FORMAT_NAME = FRAUD_DEMO.RAW.TRANSACTIONS_CSV_FORMAT)
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
ON_ERROR = 'ABORT_STATEMENT';
```

`PUT` is supported by SnowSQL/CLI and not by a normal worksheet. For a first run, the generated synthetic seed data avoids the need to upload a file. The seed inserts 10,000 rows into `RAW.TRANSACTIONS_RAW`, and the initial core load populates `CORE.TRANSACTIONS` with those 10,000 rows. The staging object is a view, and the analytics dynamic tables are aggregations, so they are not expected to contain 8,000 rows each.

## Exporting the core transactions to CSV

Section **08** of the SQL script unloads the core table as one CSV file with a header row into the internal stage:

```sql
COPY INTO @FRAUD_DEMO.RAW.TRANSACTIONS_STAGE/exports/transactions/transactions_
FROM (
  SELECT *
  FROM FRAUD_DEMO.CORE.TRANSACTIONS
  ORDER BY TRANSACTION_ID
)
FILE_FORMAT = (
  TYPE = CSV
  FIELD_OPTIONALLY_ENCLOSED_BY = '"'
  COMPRESSION = NONE
)
HEADER = TRUE
SINGLE = TRUE
OVERWRITE = TRUE;

LIST @FRAUD_DEMO.RAW.TRANSACTIONS_STAGE/exports/transactions/;
```

To download the staged file to your computer, use SnowSQL or Snowflake CLI and replace the directory with an absolute local path:

```sql
GET @FRAUD_DEMO.RAW.TRANSACTIONS_STAGE/exports/transactions/ file://<local-directory>/;
```

You can also run `SELECT * FROM FRAUD_DEMO.CORE.TRANSACTIONS` in Snowsight and use the results download/export control. For Streamlit, the recommended setup is to connect directly to Snowflake and query `FRAUD_DEMO.CORE.TRANSACTIONS`; the CSV is useful when you specifically need a local extract or file-based workflow.

## How processing works

### Stream and task

`TRANSACTIONS_RAW_STREAM` tracks newly inserted raw rows. The scheduled task checks `SYSTEM$STREAM_HAS_DATA` and inserts new rows into `CORE.TRANSACTIONS`, adding simple rule flags and a classification. The task is resumed by `ALTER TASK ... RESUME`.

- The stream is created **after** the initial sample rows are seeded, so it captures new changes rather than reprocessing the original sample.
- The demo stream uses `APPEND_ONLY = TRUE`; it is intended for insert-only events. Updates and deletes to existing raw rows are not part of this stream pattern.
- The sample task inserts new rows. For production-grade exactly-once/upsert behavior, add an enforced deduplication strategy such as `MERGE` keyed by transaction ID, handle late-arriving events and corrections, and define a replay/recovery plan.
- Snowflake tasks are not instantaneous. The one-minute schedule is a scheduling cadence, not a hard end-to-end latency guarantee.

### Dynamic tables

The two dynamic tables are declarative `SELECT` transformations over `CORE.TRANSACTIONS`. Snowflake manages their refreshes toward their `TARGET_LAG` freshness goals. Target lag is not a promise that refreshes occur at an exact fixed interval, and lower lag can increase compute usage.

## Fraud rules in this demo

- `HIGH_VALUE_FLAG`: amount is at least 5,000.
- `HIGH_RISK_FLAG`: risk score is at least 0.80.
- `CONFIRMED_FRAUD`: `IS_FRAUD = TRUE`.
- `SUSPICIOUS`: high risk or pending review, unless already labeled confirmed fraud.
- Otherwise: `LEGITIMATE_OR_UNCONFIRMED`.

These rules are illustrative, not a substitute for model validation, investigation workflows, or bank policy. A high-risk score is not proof of fraud.

## Useful queries

```sql
-- Overall KPIs
SELECT * FROM FRAUD_DEMO.ANALYTICS.V_FRAUD_DASHBOARD_KPIS;

-- High-risk transactions for review
SELECT *
FROM FRAUD_DEMO.ANALYTICS.V_HIGH_RISK_TRANSACTIONS
ORDER BY RISK_SCORE DESC, TRANSACTION_TS DESC;

-- Country risk summary
SELECT *
FROM FRAUD_DEMO.ANALYTICS.DT_FRAUD_RISK_SUMMARY
ORDER BY CONFIRMED_FRAUD_RATE DESC;

-- Daily volume and amount
SELECT *
FROM FRAUD_DEMO.ANALYTICS.DT_DAILY_TRANSACTION_SUMMARY
ORDER BY TRANSACTION_DATE DESC, TOTAL_AMOUNT DESC;
```

## Monitoring

```sql
SHOW STREAMS IN SCHEMA FRAUD_DEMO.RAW;
SHOW TASKS IN SCHEMA FRAUD_DEMO.CORE;
SHOW DYNAMIC TABLES IN SCHEMA FRAUD_DEMO.ANALYTICS;
```

Use the task and dynamic-table history queries in the SQL script to troubleshoot failures and refresh behavior. If a task is suspended, resume it with:

```sql
ALTER TASK FRAUD_DEMO.CORE.PROCESS_NEW_TRANSACTIONS_TASK RESUME;
```

## Cost and security notes

- The X-Small warehouse is intended for a small demo; suspend it when not in use. Auto-suspend is enabled.
- A running scheduled task can wake its warehouse and incur compute charges.
- Avoid real cardholder data, personal data, production credentials, or secrets in a public repository.
- Use role-based access control, masking policies, row access policies, retention controls, monitoring, and alerting before adapting this pattern to sensitive data.
- The demo has no notification integration, production SLA, model scoring service, or case-management workflow.

## Possible extensions

3. Add velocity rules (many transactions in a short window), device/account changes, geo anomalies, and card-testing patterns.

5. Connect Power BI or Tableau to the analytics views.
6. Add alerts and an investigator case queue.
